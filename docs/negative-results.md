# Negative results and do-not-repeat

Read this before proposing an implementation. Repeating a listed approach is a
waste of time unless you have new measured evidence.

Status legend:

- **CONFIRMED** — measured or directly observed
- **WRONG** — a listed verdict that later measurement disproved (kept so the
  corrected mechanism is on record)
- **DEFERRED** — deliberately out of scope for now
- **OPEN** — not yet measured; do not cite as a result

> **Correction (2026-11-18):** the keyframe `44.71 / 60.44 dB` figures in this
> document are stale. On current main the nightly key is **48.48 dB full-res /
> 64.75 dB lp8**: a **1.68 dB** gap to SVT, not 5.4 dB, with the crossover at
> ~3 px. The stream gap is the P tail, not the keyframe. See
> `docs/luma-audit.md` for the current per-segment attribution.

## Resolved encoder root causes (was CONFIRMED)

These three failures were encoder bugs, not decoder limits.  Each is now
`dav2d --strict 1` exact and gated.

| Case | Root cause | Fix / gate |
|---|---|---|
| `--video-refmvbank` diverged at the third superblock row | The base `collect_node()` never called `reset_refmvbank_for_sb()`, and the reset did not clear the §6.19.2.1 bank size/start rings at each superblock **row**; the pinned decoder clears them at `dav2d_refmvs_tile_sbrow_init()` and seeds from the row above.  The derived/bank step order was also inverted for single references (step 19 must precede step 20). | Reset at every SB, clear sizes when `mi_row` starts a row, seed from the row above, and apply the §7.12.2 step 18/19/20 order.  Gate: `video_mv_traj_gate.sh` `bank_64`, `bank_360`, `bank_360_r3` |
| `--video-mv-traj --video-refs 3` differed in one 16x16 leaf | `video_temporal_scan()` hard-coded `in.use_traj = false` and never passed `p.mv_traj`, so the §7.12.2.8 temporal candidate used the projected motion field while the decoder used `rp_traj`.  With two references the two values coincided on the gated clips. | Pass the trajectory field to the scan (`use_traj`/`traj`).  Gate: `video_mv_traj_gate.sh` `traj_360_r3` |
| 8-bit 4:0:0 `--video-pc-wiener` P frame rejected as `Error parsing frame header` | The frame header's non-PC luma LR tool list excluded PC-Wiener even though the sequence advertised it.  With both luma tools enabled (monochrome), the decoder reads f(2) `FrameRestorationType` while the encoder wrote the shorter f(1) form for NONE.  The P header was 48 bits instead of 49, so the tile started one byte early.  At 10-bit or with chroma the bit count still landed on the same byte boundary, hiding the bug. | Configure `lr_tools_disable[0][1]` from `lr_disable_luma_pc_wiener` so the frame list matches §5.4.10.  Gate: `gate_video_filters.sh` `mono pc-wiener` |

## Dark-fade chroma artifacts (video)

Symptom chased: red/cyan speckle on neutral, low-luma content (a 4K fade
downscaled to 240p, and the f44-59 tail of `testdata/nasa_480x240_30fps_60f.y4m`,
where the letterboxed text panel drops from luma 58 to 36). Every row below was
measured on that clip at `--video --qp 119 --fast-decode`, decoded with
`dav2d --strict 1`; the published decode agrees with `--video-recon`
(`dec vs recon = 0.00`), so this is an **encoder-side** decision, not a writer
or decoder defect.

Measurement conventions used here, because the obvious metrics mislead:

- Split the error into per-8x8-block **DC and AC**. The symptom is **99.8 % AC**
  (DC rms 0.05-0.08); it is *not* a colour cast. Any "dark chroma is biased"
  mechanism is therefore the wrong family.
- Score luma and chroma **separately** in the same region. Optimising one and
  reporting it is how four of these rows were mis-diagnosed the first time.
- On text, watch `corr(source high-pass, luma error)`. Healthy arms give
  **+0.11 (base) / +0.13 (SVT)**: error behaves like noise. An arm at **-0.47**
  is *subtracting* detail, which is what the eye sees as smeared glyphs.

**Where the lever actually is.** The residual arm is not broken — it is priced
against skip with the same lambda and loses ("meanJ_res 11813 vs meanJ_skip
8415"). What makes the chroma correction *worth* its bits is whatever term
raises its weight, and that term also re-prices luma. A real fix therefore has
to change the **structure**: code a chroma-only residual while keeping the
luma/mode/search decisions and reference-update accounting unchanged. That is a
design change to the leaf arm, not a weight tweak, and it is **not** proven —
the four separability attempts above all failed. For reference at f59 rate
matched to the base 24,669 B: base chroma 1.06 luma 1.41, SVT chroma **0.86**
luma 2.27. SVT holds chroma error flat through the fade (~0.85 at every frame),
which is the behaviour to match.

### Leaf-mode re-score lambda: inconsistent, but unreachable (audit of the A/A2/B phases)

### Where the probe's remaining headroom actually is (code-level, not yet built)

`partition_probe_leaf_cost` (`src/pipeline/video/video_frame.cpp:411`) prices a

both closed.

## Why f0-32 inter frames cost too much: measured drift, and why refreshing does not pay

Diagnosed 2026-11-26 on `space8k_1440x720_60f` at QP198, per-frame luma PSNR:

```
f0   33.60 dB (key, 13,465 B)   f9   31.60 dB (646 B)   f59  30.62 dB (625 B)
f1   33.66 dB (duplicate)       f11  31.43 dB (632 B)
f4   32.53 dB (new content, 520 B)
```

Two facts fall out:

1. **Duplicates inherit their reference's error exactly** (f1 33.66 ~ f0 33.60,
   f5 ~ f4, f7 ~ f6). A skip frame costs ~100 B and re-codes nothing.
2. **PSNR decays monotonically, ~3 dB over the chain.** Each new-content frame is
   coded coarsely on top of an already-degraded reference, so inherited error is
   never repaid.

That is exactly what `--video-drift-refresh` targets, so it was measured.

| Status | Do not do | Why | Do instead |
|---|---|---|---|
| CONFIRMED | Expect `--video-drift-refresh` with its defaults to help | The default `drift_refresh_qp = 0` codes the refresh residual at the *same* QP, so nothing resets: the stream is **byte-identical** (`320bdd55`) while the log still prints "drift refresh frames 8 (1587 extra payload bytes)". A no-op default plus a **reporting bug** (requests counted, not applied) -- **fixed**: the line now prints `N (M with QP drop, X B above running mean)`, so the default run reads `8 (0 with QP drop, ...)` and no longer claims a refresh it did not make. The 1,200 B default budget also rejects every refresh on this content; 8,000 B saturates at 11 frames | Set `--video-drift-refresh-qp` and raise `--video-drift-refresh-budget` |
| CONFIRMED - negative | Pay to refresh the chain at this rate | With a real QP drop the stream changes, but matched bytes loses: base 36,813 B / 7.1331 and 37,798 B / 7.2165, against refresh qpdrop10 37,952 B / **7.1489** and qpdrop16 38,704 B / 7.1615. Base interpolated to 37,952 B is **7.2295**, so the refresh arm is **-0.08 JOD**; at 36,813 B it is a tie | At ~608 B per frame, paying to reset the chain costs about what the reset saves. The deficit is structural: refresh (costly) or drift (free, but the error persists) |

**Untested follow-up this suggests:** the pulldown cadence makes ~40 % of frames
near-duplicates under 1,000 bits. A refresh scheduled on a content-change frame
(already expensive) rather than on a PSNR threshold may be much cheaper. Not
measured; do not cite as a lever.

## Cross-encoder decomposition: where a stronger encoder's advantage lives

Measured 2026-11-26 with `tools/oracle.py` on `space8k_1440x720_60f` (60 f),
matched at 294.5 kbps. `SvtAv1EncApp --preset 0 --crf 63` codes the same clip to
**36,165 B / cvvdp 8.2317 / PSNR-Y 34.64 dB** against av2enc QP200
**36,813 B / 7.1331 / 31.49 dB**: **+1.10 JOD and +3.1 dB in 648 fewer bytes**.

Cross-candidate replacement (substitute one segment of OUR decoded stream with
SVT's decoded frames; base K 44.886):

| segment | dK with SVT frames | dK with perfect source |
|---|---:|---:|
| key f0 | +0.93 | +1.81 |
| **f0-32** | **+6.48** | +18.28 |
| f33-43 | +2.19 | +5.52 |
| f44-59 | +2.34 | +7.18 |

**Pooling bounds, not encodable streams**: they say where the quality deficit
lives, not what a fix would buy.

| Status | Do not do | Why | Do instead |
|---|---|---|---|
| CONFIRMED | Attribute the cross-encoder gap to allocation, key funding or decision optimality | All three are measured and excluded: water-filling is worth +0.026 dB, every decision lever <= 0.03 JOD, and substituting SVT's KEY buys only +0.93 K (less than our own key's +1.81 headroom) | Inter frame coding in f0-32, worth +6.48 K of the gap |
| CONFIRMED | Expect AVM/AVM-class ceilings to be provable | AVM is a black box by policy and no AVM encoder binary exists here (metrics-only JSONs in `bench/avm_baseline`). "Why is theirs higher" is a claim about two artifacts, not a proposition with a proof; even our own optimality is only a conditional bound | Use SVT as a runnable black-box reference and attribute by segment, as above |

**The triangulation is the result.** Three independent methods put the deficit in
the same place: the source ceiling (+18.28 on f0-32), the per-frame bit split
(P already holds 61.8 % of the stream), and cross-encoder replacement (+6.48 K).

## Cross-encoder per-frame analysis: the deficit is uniform, and it is a per-frame floor

Measured 2026-11-26 on `space8k_1440x720_60f`, av2enc QP198 (37,798 B) against
`SvtAv1EncApp --preset 0 --crf 63` (36,165 B). Per-frame luma PSNR, ours -> SVT:

| frame class | ours | SVT | delta |
|---|---:|---:|---:|
| key f0 | 33.60 | 35.85 | +2.25 |
| near-duplicate P (12 frames, <1000 bits) | — | — | **+3.18** |
| real-content P (28 frames) | — | — | **+3.17** |
| total | 31.49 | 34.64 | +3.15 |

### It is not inter-specific (retires the earlier reading)

The segment-pooling row (f0-32 = +6.48 K with SVT frames) measures where the
*inherited* error lands, not which coder is better: a skip frame inherits its
reference's error exactly, so a better key lifts every frame downstream of it.
Per frame the deficit is the same on the key, on skips and on real inter frames.

### SVT's bit profile is structurally different

From the IVF record sizes (display order; total 35,413 B):

| | key | 2nd frame | frames >1000 B | frames <=100 B |
|---|---:|---:|---|---|
| SVT | 19,135 B (54%) | 7,456 B | 4 frames = 31,796 B (90%) | **48 frames = 853 B** |
| av2enc | 13,465 B (39%) | — | 1 (the key) | 31 frames = 4,072 B |

SVT's even display indices are **5-byte `show_existing_frame`** uncoded repeats;
its real inter frames cost 20-100 B. Ours cost 42-234 B for the same content.

|---|---|---|---|
| CONFIRMED - negative | Shift bits from inter to the key at fixed total | `--qp 204 --video-key-qp-offset -51` (key QP153) doubles the key payload (13,465 -> 21,827 B) and lands at 42,863 B / **7.5587** against a base interpolation of ~7.55: **a tie**, 17% off the operating range | The inter cost is a per-frame *floor*, not residual refinement (at QP204 the cheapest inter frame is still 56 B, median 160 B) |

No path replaces a duplicate inter frame | Wire `sef::make_sef_obu` into the low-delay P loop behind a gate |

### An exact duplicate costs ~150 B to code

Three byte-identical input frames at QP200 encode to **12,850 / 217 / 156 B**,
and the decoded f1 is *not* equal to decoded f0. So the encoder spends those
bytes coding a residual against the reconstructed reference (which differs from
the source), i.e. it pays to say "the same" and still does not converge.

### The prize: 11.3 % of the stream codes nothing worth having

At QP198, 31 of 60 frames cost <=250 B each and together hold **4,072 B
(11.7 %)**. Replacing each of them with the previous *decoded* picture (what a
`show_existing_frame` would output, without the 40-80 B inter-frame floor) then
scoring the result at the reduced byte count:

| stream | bytes | cvvdp | PSNR-Y |
|---|---:|---:|---:|
| base QP198 | 37,798 | 7.2165 | 31.486 |
| same, 31 near-duplicates collapsed | **33,881** | **7.2043** | 31.448 |
| base ladder interpolated to 33,881 B | 33,881 | **6.9613** | — |

**+0.243 JOD at matched bytes for -0.038 dB**, i.e. 22 % of the 1.10 JOD SVT gap,
and it needs no new coding tool: it needs the encoder to stop paying ~150 B to
say "same picture".

Caveats, recorded so the number is not over-read: this is an oracle-style bound
(the freed bytes are not re-spent; at the measured ~0.071 JOD per 1,000 B that
would add ~0.04 more), and it assumes a real SEF costs ~5 B, which the pinned
decoder must accept.

**Primitive check (2026-11-26):** `--video-sef` on a 2-frame input emits a
5-byte SEF record and `dav2d-macos -q --strict 1` decodes it to the expected 2
outputs, so the 5 B assumption behind the table above is measured, not guessed.
The SEF machinery (`src/codec/inter/sef/`) and the pinned-decoder compatibility
check already exist; what does not exist is a path that decides *per frame* to
emit one instead of coding a duplicate.

### Trying it: SEF *does* work -- but only the spec's explicit-hint form, which dav2d rejects

The obvious way to stop paying for duplicates is `show_existing_frame`, whose
syntax module (`src/codec/inter/sef/`) already exists. It was wired into the
low-delay P loop behind `AV2ENC_SEF_DUPLICATES=<dB>`: when the source picture is
within `<dB>` of the primary reference's reconstruction, emit a SEF instead of
an inter frame and skip the slot refresh.

The stream is syntactically fine -- 60 IVF records, SEF units exactly 5 B,
`dav2d-macos -q --strict 1` exits 0 -- but it decodes to **5 output frames, not
60**:

```
threshold 32 dB: 37,292 B, 4 SEFs,  => 5 outputs (out0..out3 = f0, out4 = f4)
threshold 30 dB: 31,984 B, 36 SEFs, => 5 outputs
```

| Status | Do not do | Why | Do instead |
|---|---|---|---|
| CONFIRMED - negative (retracted, see below) | Write the SEF header with `derive_sef_order_hint = 1` (what `sef::make_show_header` produces to satisfy dav2d) | That form re-shows a frame at **its own** order hint, so the repeat cannot occupy a new display position; with `dav2d` it decodes to 5 outputs of 60. `make_show_header` is written around a **dav2d** restriction (`cpoc != poc`), not around the spec | Signal `derive_sef_order_hint = 0` with this frame's own hint -- §5.18.2's `mixedOutput` branch exists exactly for that |

**Retraction.** The first attempt used `sef::make_show_header`, which always
signals the reference's own hint because the pinned dav2d demands it. Judged
against dav2d that produced 5 outputs of 60 and the approach was written off and
reverted. That was wrong: the restriction is dav2d's, not the spec's. Writing
`derive_sef_order_hint = 0` + `sef_order_hint = <this frame's hint>` directly,
and validating with **avmdec**, gives:

```
QP198, threshold 30 dB: 31,984 B, 36 SEFs of 5 B, avmdec 60/60 frames, exit 0
  cvvdp 7.1624  psnr_y 31.286     (base QP198: 37,798 B / 7.2165 / 31.486)
```

`tools/validate_avmdec.py` reports `60 frame(s), recon=n/a, OK`. Same quality
for 15.4 % fewer bytes; the +0.243 JOD bound above was, if anything, an
underestimate. `dav2d` still rejects these streams, which is why the validation
target is now avmdec until the dav2d pin moves.

`AV2ENC_SEF_DUPLICATES=30` on `space8k_1440x720_60f`, decoded with `avmdec`,

|---|---:|---:|---:|---:|---:|
| base QP198 | 37,798 | 7.2165 | 31.486 | -- | -- |

| SEF QP194 | 35,119 | **7.3425** | 31.613 | 7.0188 | **+0.324** |
| SEF QP198 | 31,984 | 7.1624 | 31.286 | 6.8346 | +0.328 (extrapolated) |

All three arms decode to 60/60 frames with `avmdec`, and
`tools/validate_avmdec.py` reports `60 frame(s), recon=n/a, OK`. Nothing else
tried this session comes close: the best other lever (probe chroma costing) is
+0.027 JOD on this stream, ~10x smaller.

**Limits, so this is not over-claimed.** One clip, and one with a pulldown
cadence (36 of 60 frames are near-duplicates). The trigger is a luma-PSNR
threshold against the primary reference -- cheap, but it is a content
heuristic, not an RD decision, so the threshold needs a second clip (e.g. the
active loral segments) before it is trusted, and it is not enabled by default.
It also cannot help content with no duplicates, which is most real footage;
this is a *pulldown/frozen-content* win, not a general coding-efficiency win.

**Retires the earlier plan:** force-skip (estimated ~+0.11 K) is unnecessary;
the SEF form is strictly better because it removes the 40-80 B inter-frame
floor as well as the residual.
