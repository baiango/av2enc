# Flame graph — `--nightly-b`, one encode

Generated 2026-11-24 on the Apple M4 dev host from a real `sample` capture of
one encode. Artifact: `nightly-b-24f-qp119-8t-work.svg` (this directory),
generated by `sample_to_flamegraph.py`.

## Recipe

```sh
# A -g build: `sample` resolves stacks to functions only with debug info.
cmake -S . -B /tmp/fg/build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
      -DAV2ENC_ENABLE_CUDA=OFF -DAV2ENC_ALLOW_CPU_ONLY=ON \
      -DCMAKE_CXX_FLAGS="-g -fno-omit-frame-pointer" \
      -DCMAKE_EXE_LINKER_FLAGS="-g"
cmake --build /tmp/fg/build -j8 --target av2enc

/tmp/fg/build/av2enc testdata/nasa_480x240_30fps_60f.y4m -o /tmp/fg/out.ivf \
    --video --frames 24 --qp 119 --cpu-threads 8 --video-gops 3 --nightly-b &
PID=$!
sleep 2
sample $PID 20 1 -mayDie -file /tmp/fg/sample.txt
wait $PID

python3 docs/profiles/sample_to_flamegraph.py /tmp/fg/sample.txt out.svg
```

24 frames at QP119 with 8 threads; the stream is `af0f494d…`. The capture is
16,191 samples per thread at 1 ms.

## Reading it

`sample` counts are **inclusive**, and its call tree is rendered as a line
drawing whose characters the man page calls arbitrary — so the converter
takes the *column of the count* as the level, then derives self time as
`inclusive − Σchildren`. It also rejects an attachment that would over-count
its parent, because `sample` appends a flat "leaf subtree" summary after the
last thread that otherwise nests under it. A correctly parsed capture reports
**0 over-counted nodes**; the converter prints that number so a bad parse is
visible rather than shipped.

## What it shows

Two views matter, and the honest one is the second.

**All threads** — 129,528 samples of self time. **84.5 %** is
`__psynch_cvwait`: pool workers parked in `condition_variable::wait` because
the joint-plan walk is serial and only the inner candidate loops use the pool.
That is wall-clock the encode spends with 7 of 8 cores idle, not work.

**Work only** (the committed SVG, idle waits removed) — 17,366 samples:

| frame | samples | note |
|---|---:|---|
| `IFE::joint_p_decide_sb` | 7,589 | 44 % of all work |
| — `joint_p_measure_leaf` → `collect_node` → `encode_leaf` | 6,464 | the trial amplification |
| — `search_luma_tx` (`txtsearch::search`) | ~5,300 | inside the leaf encode |
| `txv::forward_block` / `inverse_block` | — | the transform pair |
| `rdoq::Model::init` | — | rebuilt per coefficient block |

This independently confirms the numbers the built-in stage timers gave
(`AV2ENC_RD_JOINT_P_PROFILE`): the joint solve is ~95 % of the encode, the
leaf encode is ~95 % of the solve, and the luma TX search is roughly half of
that. `write()` (entropy) does not appear at all.

It also shows the shape of the parallelism problem: a deep single call chain
(`main → decide → joint_p_decide_sb → measure_leaf → encode_leaf → search_luma_tx`)
with worker threads parked beside it. Widening that chain is what the batch
attempted and what the wavefront and the verification gate could not do
(`docs/negative-results.md`, 2026-11-24 rows).

## Caveats

- Sampling is statistical at 1 ms; frames thinner than ~0.1 % may be absent.
- `--frames 24` rather than the pinned 60 keeps the capture short; the stage
  shares match the 16 f profile, so the shape is representative.
- This host is the CPU correctness oracle, not the product target. A CUDA
  build would look completely different.
